# Drakkar ERP — Soft

Рабочий архитектурный прототип покрывает рисковые механизмы Drakkar ERP, а не весь будущий продукт.

Реализованы:

- UC6/UC7: назначение в команду, подтверждение участия и обнаружение конкурентного изменения;
- UC11/UC12: атомарное списание ресурсов и перевод корабля на новый этап, блокировка финала без благословения;
- флот похода из нескольких кораблей, расчёт готовой и плановой вместимости;
- добавление и снятие кораблей на этапе подготовки, запуск только при готовом флоте и подтверждённой команде;
- запрос ярла на новый корабль: тип определяет вместимость и рецепт, заказ связывает поход с верфью;
- UC4: предварительный расчёт и атомарная фиксация Вергельда, неизменяемость итогов;
- авторизация с ролевым доступом и серверными сессиями;
- автоматическое определение поселения по учётной записи и изоляция походов, склада, верфи и аудита;
- отзыв сессии при выходе: в базе хранится только SHA-256 хеш токена;
- аудит ключевых бизнес-событий.

## Запуск

Нужен Docker с Compose:

```bash
cd soft
cp .env.example .env
docker compose up --build
```

Перед запуском нужно заменить `DB_PASSWORD` и `PROVISIONING_KEY` в локальном `.env`. Файл `.env` исключён из Git. Spring получает подключение к БД и операторский ключ через переменные окружения, перечисленные в `application.properties`; значений секретов по умолчанию в коде и Compose нет.

Интерфейс: `http://localhost:8088`.

В runtime два контейнера: один Java-процесс раздаёт React SPA и REST API, второй содержит PostgreSQL. Node.js нужен только на стадии сборки.

### Демо-учётные записи

| Роль | Логин | Пароль |
|---|---|---|
| Ярл Каттегата | `ragnar` | `raven-2026` |
| Воин | `halvdan` | `shield-2026` |
| Кораблестроитель | `floki` | `oak-2026` |
| Жрец | `godi` | `blot-2026` |
| Ярл Бирки | `erik` | `birka-2026` |

Экран входа выполняет реальную аутентификацию по логину и паролю. После входа сервер сам определяет поселение и роль пользователя. Другие поселения интерфейс и обычный API не показывают.

Демо-набор Каттегата содержит шесть походов: два одновременно находятся в плавании, два готовятся и два завершены. Поход к Шетландским островам полностью готов и позволяет сразу показать действие «Начать поход». В поход к Уэссексу назначены два корабля. Для Нортумбрии показаны строящийся корабль и нехватка мест. События ярла, воина, кораблестроителя и жреца отображаются внутри карточек соответствующих походов.

Бирка уже добавлена как второе изолированное поселение. Вход `erik` показывает другой поход, корабль и склад; данных Каттегата в ответе API нет.

## Подключение нового поселения

Это отдельная операторская операция, а не пользовательский экран. Она одной транзакцией создаёт пустое пространство поселения, склад и первую учётную запись ярла:

```bash
curl -X POST http://localhost:8088/api/provisioning/settlements \
  -H 'Content-Type: application/json' \
  -H "X-Provisioning-Key: $PROVISIONING_KEY" \
  -d '{"settlementName":"Хедебю","jarlDisplayName":"Харальд Хедебюский","username":"harald","password":"hedeby-pass-2026"}'
```

Ключ задаётся переменной `PROVISIONING_KEY` в `.env`. После подключения ярл входит с созданными данными и видит только новое поселение. Для рабочего размещения нужно заменить демонстрационные пароли и ключ.

## Сценарий демонстрации

1. Войти как ярл Каттегата. В «Походах» показать компактный список: Уэссекс и Оркнейские острова одновременно находятся в плавании.
2. Выбрать Шетландские острова: все проверки готовы, кнопка «Начать поход» активна. Снять корабль и вернуть его, чтобы показать пересчёт готовности, затем начать поход.
3. Выбрать Нортумбрию: готово 20 из 70 мест, с учётом строящегося корабля — 60. Запросить ещё один кнорр; интерфейс заранее показывает его рецепт.
4. Открыть «Ресурсы»: остатки склада отделены от верфи, рядом видны нормативы кнорра и драккара.
5. Войти как кораблестроитель: заказ содержит название связанного похода. Закрыть этапы; финальный этап потребует Блот.
6. Войти как жрец, подтвердить Блот, затем вернуться к кораблестроителю и закрыть этап.
7. В «Команде» назначить свободного жителя, затем войти как воин и подтвердить участие.
8. Под ярлом зафиксировать итоги похода и открыть «Историю»: завершённые походы идут списком, аудит находится внутри выбранной карточки.
9. Войти как `erik` и показать, что система автоматически открыла Бирку с другим походом и складом.

Исходные данные Каттегата восстанавливаются из «Обзора» под ролью ярла.

## Проверки

Backend:

```bash
cd soft/backend
mvn test
```

По умолчанию интеграционные тесты поднимают временный PostgreSQL 16 через Testcontainers. Для CI также поддержаны `TEST_DATABASE_URL`, `TEST_DATABASE_USER` и `TEST_DATABASE_PASSWORD`.

Frontend:

```bash
cd soft/frontend
npm ci
npm run build
npm audit --omit=dev
```
