# Drakkar ERP — Soft

Рабочий архитектурный прототип покрывает рисковые механизмы Drakkar ERP, а не весь будущий продукт.

Реализованы:

- UC6/UC7: назначение в команду, подтверждение участия и обнаружение конкурентного изменения;
- UC11/UC12: атомарное списание ресурсов и перевод корабля на новый этап, блокировка финала без благословения;
- UC4: предварительный расчёт и атомарная фиксация Вергельда, неизменяемость итогов;
- авторизация с ролевым доступом и серверными сессиями;
- автоматическое определение поселения по учётной записи и изоляция походов, склада, верфи и аудита;
- отзыв сессии при выходе: в базе хранится только SHA-256 хеш токена;
- аудит ключевых бизнес-событий.

## Запуск

Нужен Docker с Compose:

```bash
cd soft
cp .env.example .env
docker compose up --build
```

Интерфейс: `http://localhost:8088`.

В runtime два контейнера: один Java-процесс раздаёт React SPA и REST API, второй содержит PostgreSQL. Node.js нужен только на стадии сборки.

### Демо-учётные записи

| Роль | Логин | Пароль |
|---|---|---|
| Ярл | `ragnar` | `raven-2026` |
| Воин | `halvdan` | `shield-2026` |
| Кораблестроитель | `floki` | `oak-2026` |
| Жрец | `godi` | `blot-2026` |

Экран входа выполняет реальную аутентификацию по логину и паролю. После входа сервер сам определяет поселение и роль пользователя. Другие поселения интерфейс и обычный API не показывают.

## Подключение нового поселения

Это отдельная операторская операция, а не пользовательский экран. Она одной транзакцией создаёт пустое пространство поселения, склад и первую учётную запись ярла:

```bash
curl -X POST http://localhost:8088/api/provisioning/settlements \
  -H 'Content-Type: application/json' \
  -H 'X-Provisioning-Key: change-this-provisioning-key' \
  -d '{"settlementName":"Бирка","jarlDisplayName":"Эрик Биркский","username":"erik","password":"birka-pass-2026"}'
```

Ключ задаётся переменной `PROVISIONING_KEY` в `.env`. После подключения ярл входит с созданными данными и видит только новое поселение. Для рабочего размещения нужно заменить демонстрационные пароли и ключ.

## Сценарий демонстрации

1. Войти как ярл и назначить свободного жителя в «Экспедицию в Нортумбрию».
2. Выйти, войти как воин и подтвердить участие. Защита от двух конкурентных ответов проверяется интеграционным тестом `staleParticipationDecisionIsRejected`.
3. Войти как кораблестроитель и закрыть два этапа. На финальном этапе сервер потребует Блот.
4. Войти как жрец, подтвердить Блот, затем вернуться к кораблестроителю и закрыть этап.
5. Войти как ярл, указать добычу и потери, получить предварительный расчёт Вергельда и утвердить итоги. Форма станет read-only.
6. Открыть «Историю» и показать след операций своего поселения.

Исходные данные Каттегата восстанавливаются из «Обзора» под ролью ярла.

## Проверки

Backend:

```bash
cd soft/backend
mvn test
```

Интеграционные тесты поднимают временный PostgreSQL 16 через Testcontainers.

Frontend:

```bash
cd soft/frontend
npm ci
npm run build
npm audit --omit=dev
```
