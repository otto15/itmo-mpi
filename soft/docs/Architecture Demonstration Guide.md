# Демонстрация архитектурно значимых сценариев Drakkar ERP

## Что нужно доказать

Демонстрация должна показывать не количество экранов, а поведение системы в рискованных ситуациях:

1. сервер сам определяет роль и поселение пользователя;
2. данные другого пользователя и другого поселения не выдаются;
3. конкурентное изменение не перезаписывает уже сохранённое решение;
4. связанные изменения выполняются одной транзакцией;
5. обязательное бизнес-правило действует на сервере;
6. утверждённые результаты становятся неизменяемыми;
7. ключевые действия оставляют аудиторский след.

Рекомендуемое время основной демонстрации — 12–15 минут.

## Все ли архитектурно значимые UC покрыты

Да, выбранные архитектурные риски покрыты. Но это не означает, что Soft реализует полные спецификации всех двенадцати продуктовых UC.

Корректная формулировка для защиты:

> В Soft реализованы архитектурные срезы UC4, UC6, UC7, UC11 и UC12, а также сквозные сценарии авторизации и изоляции поселений. Они демонстрируют выбранные архитектурные решения; остальные продуктовые функции остаются за границами прототипа.

Сценарий считается архитектурно значимым, если ошибка в нём требует изменения архитектуры, а не только добавления экрана или CRUD-операции. Для Drakkar ERP это конкурентный доступ, несколько согласованных изменений в БД, обязательное правило на стороне сервера, защита данных и неизменяемая история.

### Матрица архитектурного покрытия

| Сценарий | Архитектурный риск | Проверяемый результат | Статус |
|---|---|---|---|
| UC6 — формирование команды | Один житель не должен одновременно попасть в несколько активных походов | Повторное назначение отклоняется с `WARRIOR_ALREADY_ASSIGNED`, состав не дублируется | Покрыт архитектурный срез |
| UC7 — подтверждение участия | Два клиента могут ответить по одной устаревшей версии | Первый ответ сохраняется, второй получает `409 STALE_CREW_ASSIGNMENT` | Покрыт архитектурный срез |
| UC11 — этап строительства | Списание склада и переход корабля не должны расходиться | При успехе меняются и склад, и этап; при дефиците не меняется ничего | Покрыт архитектурный срез |
| UC12 — Блот | Финальный этап нельзя защищать только кнопкой в UI | Без Блота сервер возвращает `BLESSING_REQUIRED`; после Блота этап завершается | Покрыт |
| UC4 — фиксация итогов | Добыча, потери, Вергельд, склад и статус должны фиксироваться согласованно и навсегда | После утверждения создаются выплаты, пополняется склад, поход становится read-only | Покрыт архитектурный срез |
| Авторизация и роли | Скрытия кнопки недостаточно для защиты | Воин не получает склад, верфь, аудит и чужие назначения; отозванный токен получает `401` | Покрыт |
| Изоляция поселений | Тиражируемое приложение не должно смешивать данные клиентов | Пользователь не видит список поселений; UUID чужого объекта возвращает `404` | Покрыт |
| Аудит | Ключевые изменения должны оставлять согласованный след | Успешные операции появляются в истории текущего поселения, отклонённые — нет | Покрыт |

### Граница относительно всех продуктовых UC

| UC | Покрытие Soft | Что реализовано | Что вне прототипа |
|---|---|---|---|
| UC1 — создание похода | Нет | Демо-походы создаются фикстурой | Пользовательское создание и редактирование |
| UC2 — сводка готовности | Частично | Обзор команды, корабля, склада и активного похода | Полная модель готовности маршрута и стартовых блокеров |
| UC3 — запуск похода | Нет | Статус `SAILING` есть в демо-данных | Команда запуска и проверки допуска |
| UC4 — фиксация итогов | Архитектурный срез | Добыча, потери, preview Вергельда, атомарная фиксация, read-only | Отдельный алерт убыточного похода и команда отмены preview |
| UC5 — история походов | Частично | Завершённый поход, результаты и журнал событий | Отдельный архив, фильтры и аналитика |
| UC6 — формирование команды | Архитектурный срез | Добавление, роль, проверка занятости, состав | Удаление участника |
| UC7 — подтверждение участия | Архитектурный срез | Личное назначение, подтверждение, отказ, конфликт версии | Отдельное уведомление ярлу об отказе |
| UC8 — маршрут | Нет | Цель похода отображается текстом | Точки, расстояния и редактирование маршрута |
| UC9 — склад | Частично | Просмотр; изменения внутри UC4 и UC11 | Ручной приход и корректировка ресурсов |
| UC10 — резервирование | Нет | Требования этапа сравниваются с остатком | Отдельные резервы под походы и верфь |
| UC11 — этапы корабля | Архитектурный срез | Этапы, требования, списание, rollback, версия | Создание проекта нового корабля |
| UC12 — Блот | Да | Подтверждение жрецом и серверный запрет финала | Существенных пробелов в описанном UC нет |

Такое покрытие достаточно именно для Soft как архитектурного прототипа. Называть его полным MVP пока нельзя.

## Подготовка

Запустить приложение:

```bash
cd soft
cp .env.example .env
docker compose up --build
```

Открыть `http://localhost:8088`. Перед демонстрацией войти как ярл и на экране «Обзор» нажать «Восстановить исходные данные». Это возвращает Каттегат в заранее проверенное состояние.

### Демо-учётные записи

| Роль | Логин | Пароль | Для какого шага |
|---|---|---|---|
| Ярл | `ragnar` | `raven-2026` | UC6, UC4, аудит, сброс данных |
| Воин | `halvdan` | `shield-2026` | UC7 и ограничение данных |
| Кораблестроитель | `floki` | `oak-2026` | UC11 |
| Жрец | `godi` | `blot-2026` | UC12 |

## Пошаговый сценарий

### 1. Авторизация, роли и область поселения

1. Войти как `halvdan`.
2. Обратить внимание на название «Каттегат» в шапке: пользователь его не выбирал.
3. Открыть «Команда»: отображается только личное назначение Хальвдана.
4. Перейти в «Верфь», «Итоги» и «Историю» и показать отсутствие привилегированных данных.

Сказать во время показа:

> Роль и поселение берутся из проверенной серверной сессии. Клиент не передаёт `settlement_id`, не получает список поселений и не может расширить область запроса.

Ожидаемый результат: воин видит одно своё назначение; `ship` отсутствует, склад, доступные пользователи и аудит возвращаются пустыми.

### 2. UC6 — формирование команды

1. Выйти и войти как `ragnar`.
2. Открыть «Команда».
3. Выбрать доступного жителя, указать роль в походе и нажать «Добавить».
4. Показать нового участника со статусом «Ожидает ответа».

Сказать во время показа:

> Сервер блокирует запись членства жителя, проверяет активные назначения и только затем создаёт новое. Поэтому два ярла не смогут одновременно назначить одного жителя в разные активные походы.

Повторное назначение занятого жителя защищено кодом `WARRIOR_ALREADY_ASSIGNED` и отдельным интеграционным тестом; UI заранее исключает занятого жителя из списка.

### 3. UC7 — подтверждение участия

1. Выйти и войти как `halvdan`.
2. Открыть «Команда».
3. Нажать «Подтвердить».
4. Показать, что назначение принадлежит именно Хальвдану и получило статус «Подтверждено».

Сказать во время показа:

> Сервер проверяет не только роль воина, но и принадлежность назначения текущему пользователю. Обновление содержит условие `version = expectedVersion`, поэтому устаревший конкурентный запрос не может перезаписать уже сохранённый ответ.

Конфликт двух запросов не вынесен в пользовательский интерфейс. Его можно показать отдельным интеграционным тестом:

```bash
cd soft/backend
mvn -Dtest=ArchitectureSliceIntegrationTest#staleParticipationDecisionIsRejected test
```

Тест дважды отправляет решение с одной ожидаемой версией: первый вызов сохраняется, второй получает `STALE_CREW_ASSIGNMENT`. Для повторного живого показа восстановить демо-данные под ярлом.

### 4. UC11 и UC12 — транзакция верфи и Блот

1. Войти как `floki` и открыть «Верфь».
2. Запомнить остатки требуемых ресурсов и текущий этап.
3. Дважды нажать «Завершить этап»: корабль дойдёт до финального этапа, остатки уменьшатся.
4. Нажать «Завершить этап» ещё раз. Сервер должен вернуть `BLESSING_REQUIRED` с сообщением об ожидании жреца.
5. Выйти, войти как `godi`, открыть «Верфь» и нажать «Подтвердить Блот».
6. Снова войти как `floki` и завершить финальный этап.

Сказать во время показа:

> `ShipyardService` блокирует корабль и нужные строки склада. Списание ресурсов, переход этапа и аудит входят в одну транзакцию. Проверка Блота выполняется сервером до списания, поэтому её нельзя обойти изменением интерфейса.

Отдельный интеграционный тест искусственно создаёт дефицит смолы и подтверждает rollback: не меняется ни этап корабля, ни даже достаточный остаток дерева.

### 5. UC4 — фиксация итогов похода

1. Войти как `ragnar` и открыть «Итоги похода».
2. Оставить добычу `100 / 50 / 10` или ввести другие неотрицательные значения.
3. Отметить одного участника погибшим.
4. Нажать «Рассчитать Вергельд» и показать распределение 20/80.
5. Подчеркнуть, что preview пока не изменил статус и склад.
6. Нажать «Утвердить итоги».
7. Показать баннер «Итоги утверждены» и заблокированные поля.

Сказать во время показа:

> Утверждение одной транзакцией фиксирует потери, записи Вергельда, пополнение склада, статус похода и аудит. После commit приложение запрещает повторную фиксацию, а trigger PostgreSQL не позволяет переписать добычу даже прямым SQL.

### 6. Аудиторский след

1. Под ярлом открыть «История».
2. Показать события назначения, ответа воина, этапов корабля, Блота и фиксации итогов.
3. Обратить внимание на роль автора каждого события.

Сказать во время показа:

> Аудит записывается той же транзакцией, что и бизнес-операция, и фильтруется по текущему поселению. Неуспешная операция не оставляет ложного события.

## Дополнительная демонстрация нескольких поселений

Этот шаг нужен только при вопросах о тиражировании приложения. Обычному пользователю операция подключения недоступна и в UI не показывается.

Создать новое поселение один раз на чистой демонстрационной БД:

```bash
curl -X POST http://localhost:8088/api/provisioning/settlements \
  -H 'Content-Type: application/json' \
  -H 'X-Provisioning-Key: local-provisioning-key' \
  -d '{"settlementName":"Бирка","jarlDisplayName":"Эрик Биркский","username":"erik_demo","password":"birka-pass-2026"}'
```

Затем войти как `erik_demo` / `birka-pass-2026` и показать:

- в шапке автоматически указана «Бирка»;
- походов и кораблей Каттегата нет;
- склад Бирки содержит собственные нулевые остатки;
- списка или переключателя поселений нет;
- кнопка восстановления демо-данных отсутствует.

Техническое доказательство более строгого случая находится в тесте `provisioningCreatesIsolatedSettlementAndItsFirstJarlAccount`: запрос объекта Каттегата с сессией Бирки получает `404`.

## Автоматическое подтверждение после живого показа

Запустить тесты:

```bash
cd soft/backend
mvn test
```

Тесты используют PostgreSQL 16 в Testcontainers. Ожидаемый итог текущей версии: `Tests run: 13, Failures: 0, Errors: 0`.

Основные проверки:

- `jarlAssignsAvailableWarriorOnlyOnceAndWritesAudit` — UC6 и аудит;
- `staleParticipationDecisionIsRejected` — UC7 и конфликт версии;
- `insufficientStockRollsBackBothStockAndStage` — rollback UC11;
- `finalShipStageRequiresPriestBlessing` — UC11/UC12;
- `finalizationCommitsLedgerAndDatabaseMakesResultsImmutable` — UC4;
- `warriorHttpViewContainsOnlyOwnExpeditionAndNoPrivilegedData` — роли;
- `provisioningCreatesIsolatedSettlementAndItsFirstJarlAccount` — поселения.

Трассировка требований:

- UC6: FR-09, FR-10, FR-12;
- UC7: FR-11, FR-12, NFR-09;
- UC11/UC12: FR-17–FR-20, NFR-08, NFR-09;
- UC4: FR-21–FR-23, FR-25, NFR-08–NFR-11;
- поселения: FR-26–FR-28, NFR-12;
- авторизация и ролевые представления: NFR-02.

## Если демонстрацию нужно повторить

1. Войти как `ragnar`.
2. Открыть «Обзор».
3. Нажать «Восстановить исходные данные».

Сброс затрагивает только демонстрационный Каттегат и не изменяет подключённые поселения.

## Финальная формулировка для защиты

> Мы не пытались реализовать весь интерфейс будущего ERP. Мы выбрали сценарии, которые проверяют архитектуру: конкурентные изменения, транзакции между несколькими таблицами, обязательное серверное правило, неизменяемые результаты, авторизацию и изоляцию клиентов. Soft воспроизводит каждую из этих ситуаций в интерфейсе и закрепляет поведение интеграционными тестами на PostgreSQL.
